## 2. 项目定位

- 名称：**livestream-fault-copilot**（直播技术支持故障排查辅助 Agent；GitHub 仓库同名，如已建仓库则以实际为准）。
- 目标：利用**结构化故障知识 + RAG + Agent + 必要的工具调用**，为直播技术支持人员提供**信息补全、历史案例检索、故障分析、排查步骤推荐**。
- 当前阶段只做 **MVP / PoC**，不追求生产级。
- 第一版仅支持 4 类常见故障：**黑屏、无声音、卡顿、断流**；入职后按真实高频故障扩展。

核心业务流程：

```text
故障描述 → 判断故障类型 → 检查信息是否完整（不完整则主动追问）
→ RAG 检索 SOP/案例/设备知识 → 判断是否需要实时工具（必要时调用）
→ 初步诊断 → 给出有依据的排查步骤 → 必要时转人工 → 输出结论与依据来源
```

> **MVP 阶段的流程终点是"输出结论与依据来源"，不做"处理结果写回知识库"**（决策 D3）。会话过程只写日志文件，不进数据库。

方法论红线：

> 遵循 **真实业务问题 → 需求分析 → 技术方案 → PoC → 验证 → 迭代**；
> 不要 **LangGraph → RAG → Agent → MCP → 找场景硬套**。不为了 AI 而 AI。

## 3. 架构与组件职责

第一版采用**模块化单体**，不做微服务。

```text
Vue3（后置）/ Swagger（现阶段）
        ↓
      FastAPI
   ┌────┼─────────┐
   ↓    ↓         ↓
 MySQL  RAG      Agent（LangGraph）
 业务   Milvus   决定下一步：追问 / 检索 / 调工具 / 诊断 / 转人工
 事实    ↑          ├─ RAG（Milvus）
        └──────────├─ Tool（第一版用模拟工具）
                   └─ 追问
```

各组件职责（这是系统设计的核心，不要混淆）：

| 组件 | 职责 |
|---|---|
| **MySQL** | 保存**业务事实和结构化数据**：故障案例（标题、现象、环境、设备、初步判断、排查步骤、最终原因、解决方案、是否验证、时间戳） |
| **Milvus** | 保存**可语义检索的知识片段**：案例片段、SOP、设备说明、操作手册、历史处理记录 + metadata |
| **RAG** | 找到与当前故障最相关的知识 |
| **LangGraph / Agent** | 决定下一步做什么：是否缺信息、是否追问、是否检索、是否调工具、能否输出诊断、是否转人工 |
| **Tool** | 获取 LLM 不知道、需实时获取的信息（网络检测、OBS 日志分析、设备/系统状态查询）；**第一版只实现一个模拟 Tool** |

数据分层原则：

> **MySQL 存业务事实，Milvus 存可检索知识，Agent 负责用知识和做决策。** 不要把数据库内容全部塞进 Milvus。

知识入库链路：`MySQL(knowledge_document) → chunk → embedding → Milvus`；检索结果携带 `source_id / source_type`，再回 MySQL 取完整业务信息。

## 5. 数据模型

**阶段 0 已确认的边界（理由与推翻条件见第 12 节，不要重新讨论）：**

- MVP 只有**一张表 `fault_case`**，且只存**已结案、已沉淀的知识**；不建工单表 / 会话表。（D1）
- **删除 `verified` 字段**。（D2）
- 所有长文本字段用 **TEXT 纯文本**，**不使用任何 JSON 字段**。（D5）
- `troubleshooting_steps` 用 `1. / 2. / 3.` 换行编号的纯文本。（D5）
- `symptom` 写作规范：**现象 + 可区分特征**，禁止只写"黑屏"这类无区分度的词。（D6）
- **一个现象有多个根因时，拆成多条 case**，不允许在一条 case 里列举多种可能。（D6）
- 数据规模：4 类故障 × 每类 3~5 个根因 ≈ **15~20 条 case**，全部为自己构造的模拟数据。

候选字段（**这是待审清单，不是答案；仍需我逐个判断去留，未定稿**）：

```text
id, fault_type, title, symptom, environment, device,
initial_judgment, troubleshooting_steps, root_cause, solution,
created_at, updated_at
```

每个字段必须回答三件事（写进 `docs/design/data-model.md`）：

| 判断项 | 说明 |
|---|---|
| MySQL 类型 | VARCHAR(n) / TEXT / ENUM / DATETIME …，并说明长度依据 |
| 是否必填 | 允许 NULL 的字段要写清"什么情况下为空" |
| 服务对象 | 业务事实 / RAG 切片 / metadata 过滤 / Agent 判断 / 仅展示（可多选，须标主用途） |

> **规则：五种服务对象一个都选不上的字段，必须删掉。**

**受控词表**（必须在 `docs/design/data-model.md` 中列全，禁止自由文本）：`fault_type`、直播平台、操作系统、设备类型。
理由：自由文本会产生 `Win11 / Windows 11 / win 11` 这类脏数据；MVP 期无害，但将来做 metadata 过滤前必须全量清洗。现在列清单只是 10 分钟成本。

**实习阶段的故障记录表**（日期、平台、推流软件、排查过程、处理耗时、是否可标准化、备注）**MVP 不建**，入职后按真实业务再评估。（D1）

## 8. MVP 验收标准

不用"用了多少框架"评价项目，而看：

- **业务价值**：是否真正解决排查问题；
- **检索质量**：能否找到正确案例/SOP；
- **Agent 决策质量**：是否知道何时追问、检索、调工具、转人工；
- **可靠性**：有无胡乱诊断（信息不足时是否宁可追问也不编造）；
- **可解释性**：结论是否给出依据与来源；
- **工程质量**：数据、API、异常处理、日志、部署是否合理；
- **可维护 / 可迁移**：新增故障类型是否方便，换业务能否复用设计。

PoC 阶段应给出简单量化结果（如自建 N 个故障 case 的诊断/检索命中率、平均排查步骤数），不要只用"效果很好"描述。

**评估口径（现在即生效，否则量化结果会自欺）—— 决策 D8：**

- 入库 N 条 case，**另外单独构造 M 条不在库里的故障描述作为查询集**。严禁从已入库 case 改写查询：那等于用训练数据测训练数据，命中率必然虚高，还会掩盖真实问题。
- 每条查询必须**预先标注**"应该命中哪条 case"，否则无法判定是否命中。
- 命中率**按 `fault_type` 分组统计**，用来定位哪一类知识写得不够好，不要只报一个总数。
- 建议规模：N = 15~20 条 case，M = 20~30 条查询。

## 11. GitHub 与数据安全

**仓库现状**：本地已 `git init`（分支 `main`），已有 2 个 commit（`chore: bootstrap repository…` / `docs: add project context…`）；`.gitignore`、`.gitattributes`、`README.md`、`docs/design/` 三份骨架均已就位。**远端 GitHub 仓库待创建，尚未 push。**

- 远端仓库：`https://github.com/<我的用户名>/livestream-fault-copilot`，可见性 **Public**，建仓时**不勾选**任何初始化文件（README / .gitignore / license 都不勾），否则远端会多出一个本地没有的 commit，导致 push 被拒或产生无意义的 merge commit。
- commit 邮箱使用 GitHub 的 `<id>+<用户名>@users.noreply.github.com`，不用学校或常用邮箱 —— public 仓库的 commit 作者信息对外可见。
- **行尾统一 LF**：仓库根目录有 `.gitattributes`（`* text=auto eol=lf`）。本机 `core.autocrlf=true` 会在检出时把 LF 换成 CRLF，Windows 上写 Python/Markdown 无害，但 Step 14 用 Docker 时 `#!/bin/bash\r` 会导致容器启动失败、且报错完全看不出是行尾问题。**用 `.gitattributes` 而不是 `git config core.autocrlf false`：前者是仓库级规则，随仓库传播到任何机器与任何协作者；后者只对本机生效。**
- **`.env` 必须在第一次 commit 之前就被忽略**：一旦被提交过，事后再加进 `.gitignore` 无效，密钥已进入历史，必须重写历史 + 作废密钥重发。
- **commit 信息语言约定：英文 type 前缀 + 中文描述。**
  前缀只用 `feat: / fix: / docs: / chore: / refactor: / test:`，这是 Conventional Commits 规范，changelog 生成器、语义化版本工具、CI 都会解析它，翻成中文工具就不认；描述用中文，因为这个公开仓库的目标读者是国内面试官与同事。
  格式：`type: 中文描述`（冒号后一个空格，句末不加句号）。将来若给国际开源项目提交 PR，再改回全英文。
- 用正常 commit 记录演进，例如：
  `初始化仓库 → 设计故障案例数据模型 → 实现故障案例 CRUD → 知识入库处理 → Milvus 检索 → 实现 RAG → LangGraph 最小流程 → Agent 追问 → Tool Calling → 测试与评估 → 更新 README`。
- **commit 粒度的判断标准：能不能单独 revert。** 回滚 A 而不回滚 B 会让仓库处于不一致状态（文档指向不存在的文件、代码调用不存在的函数），A 和 B 就该在同一个 commit；两者互不影响就该拆开。禁止"一次性上传整个项目"。
- **重写历史的唯一免费窗口是 push 之前。** 一旦推到远端（尤其是有他人 clone 之后），不要为了改措辞而 force push。
- README **当前只写最小版**（业务问题、当前阶段、技术栈、文档索引）。第 11 节原来列的完整 README 结构（架构、数据模型、Agent 流程、RAG 流程、Tool、API、测试、已知问题、设计决策、未来方向）是**项目最终态**清单，随开发进度逐步补齐，不要现在写空标题占位。
- **数据红线**：当前版本只用**自己构造的模拟故障数据**。入职后绝不把公司真实内部资料、客户信息、设备敏感信息、账号、内部 SOP、日志提交到公开 GitHub；展示公司项目只能用明确允许公开的数据 / 完全脱敏 / 模拟数据。公开仓库与公司内部系统严格分离。
- **Public 仓库纪律**：一旦 public，从第一天起只能放模拟数据。git 历史删不干净（force push 重写后仍可能被 fork 或缓存），所以纪律必须是"**从来不放进**"，而不是"放进再删"。

## 12. 设计决策记录（Decision Log · 追加式）

每条决策包含三项：**结论 / 理由 / 推翻条件**。
**推翻条件是关键**：它让"以后要不要改"变成一个可判断的问题，而不是靠感觉或靠"看到别人这么用"。

新决策往后追加编号（D11、D12…），**不修改、不删除已有条目**；若某条被推翻，保留原文并在其下追加"已于 YYYY-MM-DD 被 Dxx 推翻，原因：…"。

---

### D1 · MVP 只用一张 `fault_case` 表，只存已结案知识

- **结论**：不建工单表、不建会话记录表；表里每一条都是"已沉淀、可直接被检索"的知识。
- **理由**：工单与知识的生命周期不同 —— 工单结案前没有 `root_cause`，知识条目不该有"处理耗时"。MVP 的价值在于验证"检索 + 决策"能否跑通，不在于工单系统。
- **推翻条件**：实习后发现真实场景必须记录未结案工单，且需要按处理状态查询。

### D2 · 删除 `verified` 字段

- **结论**：第一版不要这个字段。
- **理由**：全部数据是自己构造的模拟数据，该字段取值恒定、**没有区分度**；无区分度的字段等于不存在。加/删字段的成本都只是一条 ALTER，所以现在删是零风险。
- **推翻条件**：拿到真实数据后，确实存在"方案已验证有效 / 仅为推测"的区别，且需要用它影响检索排序。

### D3 · MVP 不做诊断结果写回知识库

- **结论**：流程终点是"输出结论 + 依据来源"；会话过程只写**日志文件**，不进数据库。
- **理由**：写回会形成**自我污染循环** —— 本次的错误诊断变成下次检索命中的"历史案例"，还带着来源、看起来可信。安全写回需要审核、结案、错误数据下线机制，那属于知识运营，MVP 不该碰。
- **推翻条件**：有真实用户，且已建立人工审核与错误数据下线机制。

### D4 · Milvus 中每条 case 只存 1 个向量（现象片）

- **结论**：向量内容 = `symptom` + `environment` + `device` 拼成的一段文本；命中后用 `source_id` 回 MySQL 取**整条**记录交给 LLM。
- **理由**：① 用户查询天然是现象描述，**检索空间的语义分布必须与查询分布一致**，混入 solution 会稀释相似度；② 直接落地"MySQL 存业务事实、Milvus 只做索引"的分层原则；③ 免去"该把哪个 chunk 喂给 LLM"的去重、排序、兜底逻辑。
- **推翻条件**：出现大量"直接问处置方法"的查询（如"HDMI 有信号但 OBS 无画面怎么查"）导致现象片召回不到 —— 那时才为 `troubleshooting_steps` 单独建索引片。

### D5 · 长文本一律 TEXT 纯文本，不使用 JSON 字段

- **结论**：`troubleshooting_steps` 等用 `1. / 2. / 3.` 换行编号的纯文本；整表 MVP 阶段没有任何 JSON 列。
- **理由**：JSON 要在写入序列化、读取反序列化、喂给 LLM 前转文本这三处付成本，而 MVP **没有任何一处需要"按第几步"查询或统计**；且让 LLM 稳定输出结构化 JSON 是持续的报错来源（多逗号、少引号、字段名漂移）。编号文本一处存储、三处可用（人读 / embedding / API 响应）。
- **推翻条件**：需要对步骤做结构化统计（如"第 2 步最常被跳过"）或步骤级命中分析。

### D6 · `symptom` 必须含可区分特征；一现象多根因 → 拆成多条 case

- **结论**：禁止写"黑屏"这种无区分度的 `symptom`；同一现象的不同根因写成**多条 case**，每条在 `symptom` 里写清区分特征。
- **理由**：向量的区分度来自**特征**，不是"黑屏"这个词。把多种可能压进一条 case，等于把不同根因压进同一条向量，检索必然糊。拆分同时倒逼数据质量：`symptom` 的写作规范从"描述现象"升级为"描述现象 + 可区分特征"。
- **示例**：黑屏 → "OBS 预览有画面但观众端全黑"（编码/推流侧）、"摄像头源显示无信号而其他源正常"（采集卡/设备侧）、"切换场景后恢复"（场景源配置）三条独立 case。
- **推翻条件**：同一根因下的现象变体过多导致 case 数量失控 —— 此时应引入同义词/标签，**而不是合并 case**。

### D7 · 阶段 0 只产出 3 份设计文档

- **结论**：只做数据模型、业务流程、RAG/Agent 边界；LangGraph State、API、目录结构推迟到 Step 9 之前。
- **理由**：State 的形状几乎完全由"一次交互的输入输出契约"决定，API 形状由数据模型决定。在 D1~D6 未定前画 State 必然重画，是无效工作。
- **推翻条件**：数据模型与业务边界定稿后（约 Step 9 前）自然解锁。

### D8 · 评估查询集必须独立于入库 case

- **结论**：入库 N 条 case，另建 M 条**不在库里**的查询，每条预先标注期望命中的 case。
- **理由**：从入库 case 改写查询 = 用训练数据测训练数据，命中率虚高且掩盖真实问题。
- **推翻条件**：无。**这是方法论红线，不应推翻。**

### D9 · `fault_type` 单值枚举 + Agent 推断 + 检索时不做硬过滤

- **结论**：取值为 `black_screen / no_audio / lag / stream_drop / unknown`（单值）；由 Agent 推断；检索时**不加 `where fault_type = X`**，只作为 metadata 一并返回给 LLM。
- **理由**：库仅 15~20 条，硬过滤的**精度收益 ≈ 0**（Top-5 本来就基本相关），而**召回风险致命** —— 类型判错则正确 case 根本不在候选集，且失败是**静默的**（只看到"未找到相关案例"，看不到真实原因），会把我引向错误地去调 embedding 和切片。不过滤同时救活复合故障（"断流且黑屏"）。
- **`unknown` 的作用**：类型判不出来时**不许瞎猜**，填 `unknown` 并走追问。
- **`fault_type` 的三个真实用途**：① 作为上下文交给 LLM 做软判断；② 评估时按类型分组统计命中率；③ 库变大后升级为过滤条件。
- **推翻条件**：库超过 ~300 条，且评估显示 Top-5 出现明显跨类型噪声。

### D10 · 用"必填信息清单（slot）"驱动追问，不引入置信度浮点数

- **结论**：为每个 `fault_type` 定义一份必填信息清单；Agent 规则是"清单缺哪几项 → 追问哪几项"。**不设 `fault_type_confidence` 字段。**
- **理由**：LLM 自报置信度不可校准、无区分度（会稳定输出 0.8 / 0.9），且**无法评估其准确性**，对第 8 节验收标准零贡献。而缺项检查是**可单元测试**的：缺哪几项、追问几轮、是否问到点上，全都能量化。
- **推翻条件**：出现无法用清单表达的模糊场景，且有数据证明清单机制存在系统性漏检。
